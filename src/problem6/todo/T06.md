# T06 — SSE stream endpoint + fan-out

**Epic**: Problem 6 — Live scoreboard
**Depends on**: T03 (pub/sub + history), T05 (snapshot source)
**Delivers**: the "live" in live scoreboard.

## Context

The SSE pool subscribes to `leaderboard.updates` once and fans every published
delta out to all connected clients. The protocol must survive reconnects
without losing or double-delivering events: snapshot-first, heartbeat,
Last-Event-ID replay.

## Tasks

1. **Endpoint** `GET /api/leaderboard/stream`:
   - `Content-Type: text/event-stream`; disable buffering; no-cache headers.
   - On connect, immediately send `event: snapshot` with the current top 10
     (from T05's store) — the client renders without waiting for a change.
   - Subscribe to `leaderboard.updates`; each delta → `event: score_update`
     with a monotonically increasing `id` (Redis `INCR` sequence) and the
     delta payload (userId, newTotal, top10).
   - Heartbeat: `: ping` comment every 15 s.
   - `id` values also `RPUSH`ed to `sse:history:{period}` (T03) for replay.
2. **Reconnect with Last-Event-ID**:
   - Client sends the header/query `Last-Event-ID: <n>` on reconnect.
   - Server replays buffered events with `id > n` from
     `sse:history:{period}` **before** resuming live delivery; events arrive
     in order, each exactly once.
   - Gap older than the buffer (5 min TTL) → server sends a fresh `snapshot`
     and the client replaces its whole state (no double count by
     construction — state is always server-authoritative).
3. **Connection lifecycle**:
   - Per-connection heartbeat watchdog: drop connections silent for > 45 s.
   - Cap concurrent connections per server (e.g. 50k) → `503` beyond.
   - Graceful shutdown: close subscriptions, flush `sse:conn:*` state.
4. **Fan-out scale rule**: one Redis subscription per SSE server (not per
   connection); the pool scales with connections, not with publish rate.

## Acceptance criteria

- [x] Connect → `snapshot` event arrives first with current top 10.
- [x] A `complete` (T04) while connected → `score_update` arrives within
      < 500 ms (p95) with matching `id` sequence.
- [x] Disconnect, make 3 updates, reconnect with `Last-Event-ID` → exactly
      the 3 missed events replay, in order, no duplicates.
- [x] Reconnect after the buffer expired → fresh `snapshot`, client state
      replaced, totals correct.
- [x] Idle 15 s → heartbeat comment observed (test with a raw socket client).
- [x] 10k concurrent test connections hold without memory growth (soak in
      T09); `npm run typecheck` clean.

## Out of scope

- Client SDK (T07) — this is the server side of the protocol only.
- Polling fallback (T07).
