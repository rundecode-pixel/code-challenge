# T03 — Redis projection layer

**Epic**: Problem 6 — Live scoreboard
**Depends on**: T01 (Postgres exists to rebuild from)
**Delivers**: the read-optimized projection + live fan-out: ZSET leaderboards,
pub/sub, SSE history, inflight bookkeeping, and the rebuild/reconciliation
worker. **No authoritative state lives here.**

## Context

Redis serves four non-critical jobs: the read-optimized leaderboard (ZSET),
the live broadcast (pub/sub), the SSE reconnect buffer, and the best-effort
inflight cap. Anti-replay is NOT one of them — that is the `score_events`
primary key in Postgres (T04). All API modules talk to Redis through this
layer's interfaces, so the concrete client is swappable and unit tests can
inject fakes.

## Tasks

1. **Client + connection** — wrap the Redis client (e.g. `ioredis`) in
   `redis.ts` with a lazy singleton, command timeouts, and reconnect backoff.
   No network exposure: bind to the internal network, ACL user with only the
   commands the app uses.
2. **Inflight bookkeeping** (`inflightStore.ts`):
   - `add(userId, actionId)` → `SADD inflight:{userId} actionId`, member TTL
     300s; `remove(userId, actionId)` → `SREM` (called by T04 after settle);
   - `count(userId)` → `SCARD`.
   - Fail-open semantics: Redis errors propagate as "cap skipped" to the
     caller (T02), never as a hard failure.
3. **Leaderboard store** (`leaderboardStore.ts`):
   - `increment(period, userId, points)` → `ZINCRBY leaderboard:{period}`.
   - `top(period, n=10)` → ranked list with scores, rank = index+1, ties in
     insertion order.
   - Period key selection helper (`daily | weekly | all_time`).
4. **Pub/sub** (`pubsub.ts`):
   - `publishDelta(event)` → `PUBLISH leaderboard.updates <json>`.
   - `subscribe(handler)` → async iterator / callback for the SSE pool.
   - Short history ring buffer for SSE reconnect: `sse:history:{period}`,
     capped at 100 events, 5 min TTL, `RPUSH` + `LTRIM` + `EXPIRE`.
5. **Rebuild + reconciliation** (`reconcile.ts`):
   - Full rebuild: recompute `leaderboard:{period}` from Postgres
     (`SELECT user_id, SUM(points) … GROUP BY user_id` over the period's
     `score_events`) and swap the key atomically (`RENAME` to the live key).
   - Incremental sweep: keep a `sweep:cursor` (last applied `created_at`);
     each run replays `score_events` newer than the cursor into the ZSET —
     this heals the projection after any Redis outage or crash-window gap.
   - Exposed as a CLI entry point so ops can trigger it.
6. **Period rotation** hook: `rotate(period)` used by the T09 cron job.

## Acceptance criteria

- [x] `increment` + `top` round-trip: scores ranked correctly, top-10 slice
      correct, ties stable.
- [x] Publish → subscribe round-trip delivers the event; history ring buffer
      holds ≤ 100 events and expires.
- [x] Full rebuild from a seeded Postgres reproduces the same ZSET scores.
- [x] Reconciliation sweep: delete the ZSET, run the sweep → ZSET matches the
      ledger exactly (integration, real Redis + Postgres).
- [x] Inflight store: add/count/remove round-trip; member TTL expires.
- [x] All modules consume the interfaces, not the raw client — unit tests
      inject fakes without a Redis instance.
- [x] `npm run typecheck` clean.

## Out of scope

- Token issuance (T02) and the settlement path (T04) — this ticket is the
  projection layer only.
- SSE fan-out itself (T06), which only consumes `subscribe` + history.
