# T04 — Settlement (`POST /api/actions/complete`)

**Epic**: Problem 6 — Live scoreboard
**Depends on**: T02 (tokens), T03 (projection layer), T01 (Postgres)
**Delivers**: the only place in the system where points become real.

## Context

`complete` is the security-critical path. The order of operations is fixed:

1. verify token signature + expiry + claim binding,
2. **settle ledger-first**: guarded `score_events` insert + `scores` upsert in
   one Postgres transaction — the primary key is the anti-replay guard,
3. post-commit (best-effort): update the ZSET projection and publish the live
   delta.

Every rule in the threat model is enforced at one of these steps.

## Tasks

1. **Endpoint** `POST /api/actions/complete`:
   - Auth via existing JWT middleware (`sub`).
   - Body: `{ actionId, token }`, Zod-validated (UUID + JWT shape).
   - Verify token with `verifyProofToken(token, { sub, actionId })` →
     `401 INVALID_TOKEN` on any failure (signature, expiry, `sub`/`actionId`
     mismatch).
   - **Settlement (single transaction)**:
     ```sql
     BEGIN;
     INSERT INTO score_events (action_id, user_id, action_type, points, metadata)
     VALUES ($1, $2, $3, $4, $5)
     ON CONFLICT (action_id) DO NOTHING
     RETURNING action_id;
     -- no row → already settled → ROLLBACK → 409 REPLAY_DETECTED
     INSERT INTO scores (user_id, total_score, daily_score, weekly_score, updated_at)
     VALUES ($2, $4, $4, $4, now())
     ON CONFLICT (user_id) DO UPDATE SET
       total_score = scores.total_score + EXCLUDED.total_score,
       daily_score = scores.daily_score + EXCLUDED.daily_score,
       weekly_score = scores.weekly_score + EXCLUDED.weekly_score,
       updated_at = now()
     RETURNING total_score;
     COMMIT;
     ```
   - Post-commit (never blocks the response on Redis): `inflightStore.remove`,
     `leaderboardStore.increment` (3 periods), then
     `pubsub.publishDelta({ actionId, userId, points, newTotal, top10 })`.
   - Response `200 { data: { actionId, points, newTotal } }`.
2. **Error handling**:
   - Postgres down → `503` (retryable). Nothing was recorded — a later retry
     is safe.
   - Redis down after commit → still `200`. The credit is in Postgres; the
     reconciliation sweep (T03) heals the projection.
3. **Publish payload** must include the freshly computed top 10 (from the ZSET
   read) so SSE clients can update in one round trip.

## Acceptance criteria

- [x] Happy path: `start` → `complete` → `200`, `newTotal` == previous +
      points (integration test, real Postgres + Redis).
- [x] Second `complete` with the same `actionId` → `409 REPLAY_DETECTED`,
      score unchanged.
- [x] Forged/expired/tampered token → `401 INVALID_TOKEN`, no credit, no
      ledger row.
- [x] 50 concurrent `complete` for one `actionId` → exactly one `200`, 49
      `409`, ledger has exactly one row, score incremented exactly once.
- [x] Redis down at `complete` → `200`; after Redis returns, the sweep heals
      the ZSET.
- [x] `score_events` ledger row exists for every successful credit (audit).
- [x] ZSET incremented and `leaderboard.updates` published after commit.
- [x] `npm run typecheck` clean; adversarial tests (T08) re-verify.

## Out of scope

- SSE fan-out (T06) — this ticket only publishes; it does not deliver.
- Resetting period scores (T09).
