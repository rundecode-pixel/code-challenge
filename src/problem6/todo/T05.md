# T05 — Leaderboard read API

**Epic**: Problem 6 — Live scoreboard
**Depends on**: T03 (ZSET store)
**Delivers**: the query the frontend renders on first paint.

## Context

`GET /leaderboard` returns the top 10 for a period. It is the snapshot
counterpart of the SSE stream: the UI renders this immediately, then the
stream (T06) keeps it fresh. Reads must be cheap — this is a pure ZSET lookup,
no Postgres scan on the hot path.

## Tasks

1. **Endpoint** `GET /api/leaderboard?period=weekly`:
   - Zod-validated `period` enum `daily | weekly | all_time`, default
     `weekly`.
   - Read via `leaderboardStore.top(period, 10)`.
   - Map to DTO: `{ rank, userId, displayName, score }` — display name joined
     from the users table (cache names in Redis for ≤ 5 min; a leaderboard
     never needs perfectly fresh names).
   - Response shape (fixed contract for the SDK):
     `{ data: { period, generatedAt, entries: […] } }`.
2. **Cache-consistency rule**: ZSET is the answer; Postgres is the rebuild
   source (T03). If the ZSET is unavailable → `503 LEADERBOARD_UNAVAILABLE`
   with a short `Retry-After` — do not serve stale partial data silently.
3. **Auth decision**: the leaderboard is public (that is the point of a
   scoreboard) → no auth required, but the endpoint stays behind rate limits
   (per-IP, e.g. 60/min).

## Acceptance criteria

- [x] Empty store → `200` with `entries: []`.
- [x] 12 users with known scores → top 10 ordered correctly, rank starts at 1.
- [x] Tie scores → deterministic ordering (stable by ZSET rule), documented.
- [x] Invalid `period` → `400 VALIDATION_ERROR`.
- [x] ZSET unavailable (simulated) → `503`, never a wrong answer.
- [x] Response shape matches the SDK contract; `npm run typecheck` clean.

## Out of scope

- Live updates (T06 SSE).
- Rebuilding the ZSET (T03).
