# T07 — Client SDK

**Epic**: Problem 6 — Live scoreboard
**Depends on**: T04 (complete API), T05 (leaderboard API), T06 (SSE protocol)
**Delivers**: the browser-side abstraction the UI code uses — and the last
line of defense against double-submitting completions.

## Context

The UI should never talk HTTP/SSE directly. The SDK wraps start/complete, owns
the SSE connection (with polling fallback), and — critically — guarantees a
`complete` call for a given `actionId` is sent at most once even if the app
logic fires it twice (e.g. double-click, React StrictMode double-invoke).

## Tasks

1. **`startScoreEvent(actionType)`** → `{ actionId, points, token }`.
   Throws typed errors (`Unauthorized | UnknownAction | TooManyPending`).
2. **`completeScoreEvent(actionId, token)`**:
   - Internal `inFlight` map keyed by `actionId`:
     - already in flight → return the same pending promise (dedupe);
     - already succeeded (`409 REPLAY_DETECTED` counts as success) → resolve
       with the cached result without hitting the network;
      - network error (timeout/5xx) → **do not** auto-retry the POST; surface
        `RetriableError` and let the caller decide. The server-side settlement
        guard (the `action_id` key in the ledger) makes a later manual retry
        safe either way — it either credits once or returns `409`.
   - Typed errors: `ReplayDetected` (treated as success at the SDK layer),
     `InvalidToken`, `Retriable`.
3. **Leaderboard subscription**:
   - `subscribeLeaderboard(period, onSnapshot, onUpdate)` returns an
     unsubscribe function.
   - Transport selection: try SSE; on repeated failures fall back to polling
     `GET /leaderboard?period=…` every 30 s; auto-upgrade back to SSE when a
     probe succeeds.
   - Handles `Last-Event-ID` automatically across reconnects (browser
     `EventSource` supports it natively; the polling fallback tracks it
     manually).
   - Throttle renders: coalesce burst deltas to one `onUpdate` per animation
     frame.
4. **State model** — the SDK keeps the authoritative client copy:
   `{ period, entries, lastEventId }`, updated only from `snapshot` /
   `score_update` / poll responses. UI components read this store; they never
   mutate scores locally.

## Acceptance criteria

- [x] Two synchronous `completeScoreEvent` calls with the same `actionId` →
      exactly one network POST (unit test with a mocked fetch).
- [x] `409` response → resolved as success, cached; a third call makes zero
      requests.
- [x] 5xx/timeout → `RetriableError` thrown, no silent retry.
- [x] SSE connected → updates arrive live; SSE dies → polling takes over
      (integration test against the real server, killing the socket).
- [x] Deltas within one frame are coalesced into one render callback.
- [x] `npm run typecheck` clean; SDK ships as a small zero-dependency module.

## Out of scope

- UI components themselves (the problem asks for architecture, not the
  scoreboard DOM).
- Server-side changes (T04/T06 are the contract this SDK consumes).
