# T02 — Proof-token issuance (`POST /api/actions/start`)

**Epic**: Problem 6 — Live scoreboard
**Depends on**: T01 (schema exists)
**Delivers**: the server-side gate that makes score inflation impossible.

## Context

The client is untrusted. Points must be **decided by the server** and bound to
an **action id** that the ledger (T04) will accept at most once. This ticket
implements the issuance half of that design (settlement is T04). The
anti-replay guard itself lives in the `score_events` primary key, not in this
ticket.

## Tasks

1. **Scoring registry** — `scoringRegistry.ts`:
   - Map `actionType → points` (e.g. `match_completed: 100`,
     `daily_quiz: 50`).
   - `getPoints(actionType)` throws `UNKNOWN_ACTION` for unknown types.
   - Frequency rules: per-action-type max rate (e.g. `match_completed` ≤ 1 per
     30 s per user) checked against the user's recent `score_events` in the
     last interval. Kept small and explicit — this is a hardcoded rule table,
     not an engine.
2. **Token service** — `proofToken.ts`:
   - `signProofToken({ sub, actionId, actionType, points })` → HS256 JWT with
     claims `{ sub, actionId, actionType, points, iat, exp }`,
     `exp = iat + 300` (5 min), issuer/audience set to the API.
   - `verifyProofToken(token, { sub, actionId })` → rejects on bad signature,
     expiry, or claim mismatch (wrong user, wrong actionId).
3. **Inflight bookkeeping (best-effort)** — `inflightStore.ts`:
   - `add(userId, actionId)` → `SADD inflight:{userId} actionId` with member
     TTL 300s; `count(userId)` → `SCARD`.
   - This is a **DoS cap, not a security control**: on Redis error the call
     fails open (no `429`). The ledger guard in T04 is what prevents
     double-credit; this only prevents one user from piling up unbounded
     `start` calls.
4. **Endpoint** `POST /api/actions/start`:
   - Auth via existing JWT middleware (`sub` = user).
   - Body: `{ "actionType": "…" }`, Zod-validated.
   - Per-user concurrency cap: `inflightStore.count(userId)` → > 10 returns
     `429 TOO_MANY_INFLIGHT`.
   - Success → `200 { data: { actionId, points, expiresInSeconds: 300, token } }`.

## Acceptance criteria

- [x] `start` with a valid JWT returns a token whose `points` claim equals the
      registry value — **the client cannot influence it** (sending `points` in
      the body is ignored/rejected by the schema).
- [x] Unknown `actionType` → `400 UNKNOWN_ACTION`.
- [x] No auth → `401`.
- [x] 11th concurrent in-flight action → `429`.
- [x] `verifyProofToken` rejects: wrong secret, expired, wrong `sub`, wrong
      `actionId` (unit tests).
- [x] Redis down at `start` → the endpoint still works (cap skipped, no `429`).
- [x] `npm run typecheck` clean; unit tests green.

## Out of scope

- Settling the action / crediting points (T04).
- Publishing leaderboard updates (T04).
